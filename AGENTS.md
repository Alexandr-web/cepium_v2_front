# Cepium V2 Front

Фронтенд крипто-бота для торговли на споте и фьючерсах (биржи: Bybit, Binance, OKX).
Функции: авторизация, профиль, выбор биржи, мониторинг баланса/позиций/PNL, создание и редактирование конфигов.
Это только фронт. Бэкенд живёт в отдельном репозитории, общий запуск идёт через Docker.

## Стек

Nuxt 4, Vue 3 (Composition API), TypeScript, Pinia, Tailwind CSS 4 (через @tailwindcss/vite),
TanStack (@peterbud/nuxt-query), Zod 4, socket.io-client, ECharts (nuxt-echarts / vue-echarts),
VueUse, Notivue (уведомления), Vitest + @nuxt/test-utils + happy-dom. Node.js 22+. Менеджер пакетов: **yarn** (есть yarn.lock).

## Команды

- Установка: `yarn install` (postinstall сам запускает `nuxt prepare`)
- Dev: `yarn dev`
- Сборка: `yarn build`
- Тесты: `yarn test` (все), `yarn test-unit` (проект unit), `yarn test-nuxt` (проект nuxt)
- Линт с автоисправлением: `yarn lint:fix`
- Только проверка линта без правок: `yarn eslint .`
- Перед запуском eslint должна существовать папка `.nuxt/` (создаётся через `yarn nuxt prepare` или `yarn dev`), иначе конфиг не подхватится.
- Отдельного скрипта typecheck в package.json нет, vue-tsc не установлен. Не придумывай команду `typecheck`.
  Типы проверяй через eslint, тесты и внимательное чтение. Если нужна полноценная проверка, предложи пользователю добавить `vue-tsc`, но сам зависимость не ставь.
- Проект запускается через Docker вместе с бэкендом. Не пытайся поднимать docker compose, если пользователь не попросил.

## Структура (проверяй по факту, README может отставать)

Исходники лежат в `app/`, серверный слой в `server/`, тесты в `test/`.

- `app/components/` построены по Atomic Design: `atoms/` (кнопки, инпуты, заголовки), `molecules/` (поиск, карточки, формы), `organisms/` (Header, Dashboard, TradingPanel и т.д.)
- `app/pages/`, `app/layouts/`, `app/middleware/`, `app/plugins/`
- `app/composables/` (useApi, useWebSocket, useFormatter, useToast ...)
- `app/store/` Pinia-хранилища (`useUser`, `useTrading`, `useExchanges`)
- `app/api/` методы работы с API бэкенда
- `app/models/` модели, собираемые из сырых данных бэкенда
- `app/types/` интерфейсы, type aliases, enum
- `app/utils/` чистые функции-помощники
- `server/` прослойка между фронтом и внешним бэкендом
- `test/unit/` чистая логика и утилиты, `test/nuxt/` компоненты, composables, плагины (где нужны автоимпорты)
- `docs/` документация проекта, читай её перед крупными изменениями

Перед созданием нового файла посмотри, где лежат похожие, и положи рядом по тем же правилам.

## Стиль кода (обязателен, его проверяет ESLint)

- Отступы: **табы** (и в TS, и в `<template>`, и в `<script>` Vue-файлов)
- Кавычки: **двойные**
- Точка с запятой: **обязательна**
- Скобки у стрелочных функций всегда: `(x) => x`
- Висячие запятые в многострочных массивах, объектах, импортах и экспортах. В параметрах и аргументах функций запятых нет.
- Пустая строка в конце файла
- После правок прогоняй `yarn lint:fix` и проверь, что ошибок не осталось.

## Правила Vue / Nuxt

- Только `<script setup lang="ts">` и Composition API. Options API не использовать.
- Пропсы и эмиты типизируются: `defineProps<...>()`, `defineEmits<...>()`. Без `any`.
- Автоимпорты Nuxt (`ref`, `computed`, `useFetch`, composables, components) используются как есть. Не добавляй лишние явные импорты, если проект их не требует.
- Логику выноси из компонентов в composables, чистые функции в `utils/`. Компонент отвечает за отображение.
- SSR: не обращайся к `window`, `document`, `localStorage` вне `onMounted` или `import.meta.client`. Для SSR-безопасного состояния используй `useState` или Pinia.
- Данные с бэкенда проходят через `api/` и `models/`, компоненты не работают с сырыми ответами.
- Валидацию внешних данных и форм делай через Zod (v4: синтаксис отличается от v3, при сомнениях сверяйся с документацией).
- WebSocket-подписки (socket.io) обязательно отписывай при размонтировании (`onUnmounted` или `onScopeDispose`), иначе утечки и дублирующиеся события.
- Новые компоненты кладёшь в нужный уровень atoms / molecules / organisms. Atoms не импортируют molecules и organisms.
- Стили: Tailwind-классы. Не добавляй CSS-файлы и сторонние UI-библиотеки без необходимости.

## Особенности предметной области (торговый бот)

- Деньги и цены: не показывай «сырые» float. Форматирование только через общий `formatNum` / utils. Не округляй значения молча, там, где важна точность (цена ликвидации, стоп, тейк, PNL).
- Не логируй в консоль и не отправляй в UI API-ключи, токены, секреты бирж. Публичные значения в `runtimeConfig.public` не должны содержать секретов.
- Любое действие, которое меняет позиции или ордера на реальной бирже, требует явного подтверждения пользователя в UI. Не добавляй автоматических опасных действий.
- Различай биржи (Bybit, Binance, OKX) и спот/фьючерсы: не предполагай одинаковый формат данных, ищи существующие модели.

## Тесты

- Новая чистая логика: unit-тест в `test/unit/`.
- Компоненты, composables, плагины: тест в `test/nuxt/`.
- После изменения логики запускай соответствующий набор: `yarn test-unit` или `yarn test-nuxt`.
- Не удаляй и не ослабляй существующие тесты, чтобы «позеленить» сборку.

## Как работать

1. Сначала читай существующий код рядом и повторяй его стиль и структуру.
2. Делай минимальные изменения под задачу. Не рефактори соседний код без просьбы.
3. Не добавляй зависимости и не меняй версии в `package.json` без согласования.
4. Не трогай `.env`, `docker-compose.prod.yml`, `dockerfile`, `nginx.conf` без явной просьбы. Секреты не коммить и не выводи.
5. Если не уверен в API Nuxt 4, Vue, Pinia, TanStack или Zod 4, не угадывай: проверь по документации или по использованию в проекте. Версии в проекте новые, и твои знания могут быть устаревшими.
6. После изменений: `yarn lint:fix` и релевантные тесты. В ответе кратко перечисли, что изменено и что проверено.
7. Если задача неоднозначна или затрагивает торговую логику, задай вопрос, а не додумывай.

## Правила стиля, которых нужно строго придерживаться:

1. **Не используй ключевое слово `as` для приведения типов.** Вместо приведения (`value as Type`) строй код так, чтобы типы выводились или проверялись штатно: через type guards, проверки `typeof` / `instanceof` / `in`, дискриминированные объединения, `satisfies` там, где это уместно, или явно типизированные переменные и параметры.
2. **Вместо `for...of` используй `forEach`.** Перебор массивов и итерируемых коллекций оформляй как `array.forEach((item) => { ... })`. Если нужен ранний выход, опиши логику через фильтрацию или условие внутри колбэка, а не через `break`.
3. **Вместо `for...in` используй `Object.keys(obj).forEach(...)`.** Перебор ключей объекта оформляй как `Object.keys(obj).forEach((key) => { ... })`, обращаясь к значениям через `obj[key]`.
4. **Комментарии JSDoc пиши только там, где это действительно нужно:** на неочевидных функциях, нетривиальной логике, неочевидных контрактах параметров и возвращаемых значений, а также на сложных алгоритмах. Не документируй очевидный код. Каждый JSDoc-блок должен быть коротким, без воды и пустых формулировок, и содержать пример использования (`@example`), если функция не тривиальна в применении.
5. **Используй optional chaining и вызов с проверкой:** для доступа к потенциально отсутствующим свойствам применяй `obj?.a`, для вызова потенциально неопределённых функций — `func?.()`. Не заменяй их громоздкими проверками вида `obj && obj.a`, если оператор читается однозначно.

Как работать:
- Если в исходном коде есть `as`, `for...of` или `for...in`, перепиши их по правилам выше, сохранив поведение.
- Если нужен новый код, сразу пиши его в этих стилях.
- Сохраняй исходную логику и имена переменных, если пользователь не просил иного. Не добавляй лишнего рефакторинга, абстракций и функциональности сверх запроса.
- Если правило конфликтует с требуемым поведением (например, перебор, где `forEach` не может выразить логику без `break`), выбери наиболее близкое решение в духе правил и кратко поясни, почему.

## Код-ревью

Если просят ревью, только читай и не правь код. Проверяй:
типобезопасность (any, небезопасные приведения, null/undefined), реактивность, SSR-ошибки, утечки подписок (socket.io, watchers, таймеры),
обработку ошибок и состояний загрузки, точность и форматирование чисел в торговых данных, утечку секретов, соответствие стилю ESLint,
соблюдение структуры atoms / molecules / organisms и границ между api / models / types / utils, наличие тестов.
Формат ответа: блокеры, затем важное, затем мелочи. К каждому замечанию: файл и строка, проблема, почему это плохо, как исправить.
